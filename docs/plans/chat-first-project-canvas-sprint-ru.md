# Спринт «Chat-first Project Canvas»

**Статус:** согласованная продуктовая спецификация и backlog реализации  
**Владелец:** Manus AI  
**Область:** веб-интерфейс Agent Room и связанный desktop-клиент  
**Отложено:** голосовой интерфейс, OpenAI Realtime, LiveKit, UI веток Git и интеграция `entire.io`.

## 1. Главное продуктовое решение

Agent Room становится **chat-first средой для автономной работы с программным проектом**. Обычный опыт должен быть настолько же простым, как разговор в хорошем чате: пользователь формулирует мысль, получает прямой ответ и не управляет вручную моделями, planner-ом, tool calls, терминалами, Serena, Graphiti, Docker или фоновыми процессами.

Dashboard проекта — это вторая, осознанно открываемая поверхность через пункт **Project** в левой навигации. Это не страница состояния бота. Это живая визуальная модель выбранного локального или GitHub-проекта: файлы, модули, зависимости, Git-метаданные, контекст кода, заметки, задачи и связи между ними.

> **Принцип интерфейса:** пользователь видит намерение, понятный прогресс и результат. Оркестрация, выбор модели, вызовы инструментов, индексирование и локальные сервисы остаются под капотом, пока не возникает проблема, по которой пользователь может принять полезное действие.

## 2. Зафиксированная модель взаимодействия

| Область | Решение |
|---|---|
| Старт приложения | Открывается **Chat** для уже выбранного проекта. На первом запуске остаётся только выбор источника: Local folder или GitHub repository. |
| Основная навигация | Узкая левая панель с двумя рабочими разделами: **Chat** и **Project**. Settings пока не является третьей постоянной рабочей областью, а живёт во вторичном меню. |
| Верхняя строка | Показывает **название выбранного проекта**. Ветка Git в этом спринте не показывается. `entire.io` явно переносится на отдельный этап. |
| Чат | Логика как у ChatGPT: диалог, нижнее поле ввода, streaming-ответ. Обязательны Markdown, code blocks, копирование и прикрепление файлов. Визуальный язык — собственный Agent Room, а не копия ChatGPT. |
| Лёгкое общение | Приветствия, объяснения, уточнения и обычные вопросы идут по дешёвому подходящему маршруту и не запускают planner проекта. |
| Работа над проектом | Явная просьба проанализировать, создать, изменить, протестировать, закоммитить или выпустить изменения создаёт task card и запускает структурированное уточнение. |
| Сначала уточнение, затем реализация | Задача собирает вопросы, ответы, затронутые модули, критерии результата и границы работы прямо в карточке. Реализация начинается, когда картина достаточна понятна или пользователь явно разрешил продолжить. |
| Режимы approval | **Зелёный свет** разрешает согласованный объём работы. **Спрашивать перед изменениями** останавливает агента перед созданием или изменением файлов. Read-only исследование не должно шуметь в обоих режимах. |
| Видимая жизнь агента | Под релевантным сообщением ассистента показывается короткая живая строка: например, `Карта 14 файлов · Serena`. Сырой trace planner-а не показывается. |
| Dashboard по умолчанию | Проект раскладывается на атомарную карту. Выбор узла подсвечивает только его прямые связи, чтобы граф не превращался в кашу. |
| Размещение задач | Активные задачи формируют прокручиваемую правую ленту карточек. Задача может дополнительно создавать компактный sticky-marker у затронутого файла или модуля на карте. |
| Завершённые задачи | Выполненные карточки сворачиваются в **cold archive** и не загромождают активную работу. |
| Локальные сервисы | Runtime, Serena, Graphiti и Docker работают тихо в фоне. Они не должны открывать окна PowerShell, терминала или консоли. |
| Ошибка сервиса | В интерфейсе появляется ненавязчивая красная точка. При наведении или клике она открывает компактную выезжающую диагностическую строку; подробные логи остаются только в Settings / Diagnostics. |

## 3. Визуальное направление: **Obsidian Paper**

Визуальный язык объединяет спокойствие и операционную ясность Devin с контрастной редакторской уверенностью, ассоциирующейся с Anthropic. Это не неоновый «хакерский» dashboard и не стандартная копия ChatGPT.

Базовая тема — тёмная и намеренно сдержанная: почти чёрный графитовый canvas, контрастные поверхности тёплого белого для чтения, холодный cyan для взаимодействия и небольшой набор смысловых цветов. Cyan показывает навигацию, выбор и активные элементы; зелёный — здоровое/завершённое состояние; amber — необходимость решения пользователя; красный — только реальную проблему, требующую действия. Цвет не используется для украшения плотной графовой карты.

Для интерфейса и прозы используется **Inter**, для файловых путей, идентификаторов, языков, коротких системных строк и технических метаданных — **JetBrains Mono**. В Chat приоритет у воздуха и спокойного чтения. В Project — у компактной, но не перегруженной плотности. Скругления мягкие, но не игрушечные; тени неглубокие; анимация применяется только для осмысленных переходов, streaming, фокуса узла и живого статуса.

| Семейство токенов | Направление | Применение |
|---|---|---|
| Canvas | `#0B0D10`, графит | Фон приложения и поле карты |
| Surface | `#13161B` / `#191D23` | Composer, карточки, inspector |
| Основной текст | Тёплый `#F5F1E8` | Длинное чтение и иерархия |
| Вторичный текст | Нейтральный серо-синий | Метаданные, пути, время |
| Акцент действия | Ice cyan | Выбранная навигация, активный узел, primary action |
| Здоровое состояние | Сдержанный зелёный | Connected, complete, безопасная работа |
| Требуется внимание | Тёплый amber | Approval, недостающая информация |
| Ошибка | Сдержанный красный | Только actionable failure |

## 4. Спецификация рабочего пространства Chat

### 4.1. Структура

Chat — стартовая и главная рабочая область. Колонка чтения остаётся в фокусе и не делит экран с картой зависимостей. Левая навигационная rail доступна, но не отвлекает. Верхняя строка содержит название проекта и маленький indicator системного присутствия; сырые runtime-контролы в ней не показываются.

Composer закреплён снизу, поддерживает многострочный текст, markdown-friendly ввод, файлы и одну ясную кнопку отправки. Сообщения ассистента поддерживают Markdown, code blocks, копирование и ссылки на файлы проекта, когда это уместно. Под сообщением, которое сейчас генерируется или исполняется, находится одна короткая осмысленная строка активности.

### 4.2. Маршрутизация моделей и правило planner-а

Перед выделением модели или инструментов недорогой router классифицирует каждое сообщение. Обычный диалог уходит на самую дешёвую достаточную модель и не сопровождается ритуалом планирования. Запрос о проектной работе создаёт задачу в состоянии **Уточнение** и задаёт только вопросы, необходимые для закрытия существенных пробелов. Карточка задачи — durable record решений, ограничений, ответов, критериев результата и затем журнала исполнения.

Router повышает уровень модели только когда этого требуют сложность, неоднозначность, масштаб репозитория, риск или явно запрошенное высокое качество результата. Название модели, token budget, внутренний planner trace и сырой payload инструментов пользователю не показываются. Пользователь видит смысловую сводку: `Понимаю задачу`, `Читаю проект`, `Готовлю изменение`, `Нужен ваш выбор`, `Проверяю результат`, `Готово`.

### 4.3. Жизненный цикл task card

| Состояние для пользователя | Смысл | Поведение карточки |
|---|---|---|
| **Уточняем** | Для задачи не хватает контекста или решений | Показывает точные вопросы и сохранённые ответы |
| **Готово к работе** | Scope и критерии результата достаточны | Показывает короткий план и затронутые области |
| **В работе** | Агент выполняет согласованную работу | Показывает понятные milestones, а не сырые логи |
| **Нужен вы** | Нужен approval или решение | Выделяет один выбор или компактный approval control |
| **Проверка** | Результат готов к просмотру | Показывает сводку, файлы, diff/test links при наличии |
| **Готово** | Работа завершена или принята | Сворачивается в cold archive |

## 5. Спецификация рабочего пространства Project

### 5.1. Карта и фокус

Project canvas — dashboard проекта по умолчанию. Он строит атомарный граф файлов, модулей и dependency edges из выбранного workspace. Первый экран использует разумные группы и progressive disclosure вместо показа всех связей с одинаковой яркостью. При выборе узла показываются его прямые входящие и исходящие связи, а остальной граф спокойно уходит на второй план.

Узел всегда показывает имя файла, язык и размер/число строк. Hover открывает компактную summary-card: назначение файла, ключевые exports/symbols, сигнал недавних изменений и количество привязанных задач. Click открывает inspector справа, а не новое системное окно. Inspector содержит preview кода, dependency links, Git-метаданные, связанные заметки, error markers при наличии и task markers. Полноценный редактор кода откладывается; первый спринт даёт читаемый preview и точную навигацию к файлу.

### 5.2. Фильтры и смысловые группы

Карта содержит спокойные, цвето-кодированные фильтры: **Files**, **Modules**, **Dependencies**, **Git changes**, **Tasks**. Это линзы одной и той же карты, а не отдельные dashboards. Пространственный контекст сохраняется при переключении фильтров.

### 5.3. Лента задач и sticky markers

Правая лента — канонический стек активной работы. Она вертикально прокручивается, а выполненные задачи уходят в cold archive. Каждая задача может быть привязана к нулю, одному или нескольким узлам карты. Привязки показываются как минимальные sticky-markers рядом с файлом/модулем; они не должны закрывать название узла или dependency path.

Hover marker-а показывает title, текущее состояние, intent и последнюю активность. Click открывает тот же drawer задачи с ответами на уточнения, scope, approvals, milestones, логами, summary diff/test и связанными файлами.

## 6. Спецификация тихого local runtime

Runtime, Serena, Graphiti и Docker — часть реализации, а не ежедневного интерфейса. Desktop-клиент запускает их без PowerShell/terminal окон и поддерживает единый компактный статус фонового supervisor-а.

Видимая пользователю health-модель должна быть минимальной:

| Индикатор | Нормальное состояние | Состояние ошибки |
|---|---|---|
| Cloud | Зелёная точка, без лишнего текста | Красная точка открывает короткое объяснение по сети/сессии |
| Runtime | Зелёная точка, локальный сервис активен | Красная точка указывает на проблему pairing/sync |
| Serena | Зелёная точка после готовности semantic service | Amber/red только если навигация по проекту ухудшена |
| Graphiti | Зелёная точка при доступном Docker-backed profile | Neutral/amber, если Graphiti отложен из-за Docker; Chat и Project не блокируются |

Упомянутый «ключик» в интерфейсе лучше реализовать не буквально как ключ, а как **единый indicator системного присутствия**: healthy / attention needed / offline. Его задача — сообщить состояние без распухания интерфейса. Hover или click открывает компактный diagnostic sheet, а Settings хранит глубокий технический вид.

## 8. Явно исключено из этого спринта

Голос, realtime interruption, speech-to-text, text-to-speech, LiveKit и OpenAI Realtime не входят в текущий scope. Выбор ветки Git и интеграция `entire.io` сознательно отложены. Полный редактор кода, terminal emulator, generic shell, конкурентные профили нескольких workspaces и постоянно открытая diagnostics-консоль также находятся вне этого спринта.

## 9. Критерий успеха

Спринт успешен, если новый пользователь может выбрать локальный или GitHub-проект, открыть Agent Room сразу в аккуратный Chat, непринуждённо общаться без planner friction, поставить реальную задачу по проекту, которая превращается в хорошо уточнённую task card, переключиться в Project и увидеть спокойную навигируемую карту зависимостей со связанной работой — и при этом никогда не увидеть терминал, если он сам не открыл Diagnostics.

Система должна ощущаться живой благодаря короткой осмысленной активности, но тихой благодаря полной инкапсуляции оркестрации. Dashboard должен делать проект понятнее file tree, а не сложнее него.

| Решение | Зафиксированное поведение |
|---|---|
| История диалогов | В Chat доступна кнопка «Новый разговор». История диалогов хранится в контексте проекта, но не занимает отдельный пункт sidebar. |
| Большие репозитории | Для очень больших проектов сначала строится лёгкая карта файлов и верхнеуровневых зависимостей. Глубокая Serena-индексация выполняется progressive/on-demand в фоне и не задерживает открытие Chat. |
| Вложения и архивы | Chat принимает изображения, документы, аудио и архивы. По умолчанию они остаются local-first; архивная резервная копия создаётся только по явному запросу пользователя. |
| Отложенная работа | Фраза вида «пометь этот файл, вернёмся позже» создаёт отложенную task card и sticky-marker, но не запускает реализацию. |
| Commit и push | В Green light commit может входить в согласованный scope. Push в начале всегда требует подтверждения; после двух подтверждённых push Agent Room предлагает включить доверенное правило «push без повторного вопроса» для этого проекта. |
| Docker и Graphiti | Docker Desktop никогда не устанавливается молча. Если Graphiti недоступен, Settings предлагает включить память отдельно; Chat и Project продолжают работать. |
| Содержимое карты | По умолчанию показываются Git-tracked файлы. Untracked/ignored файлы раскрываются только через Git changes. |
| Тема | В первом спринте реализуется только тёмная Obsidian Paper тема. |
| Новый проект из чата | Запрос «создай новый проект» сначала создаёт clarification-first task с вопросами о цели, стеке, ограничениях и критериях результата. |
| Ask-before-changes | Read-only тесты и анализ запускаются автоматически. Approval нужен перед созданием/изменением файлов и внешними действиями. |

## 11. Правило автономного исполнения

Спринт считается завершённым только после реализации всех достижимых пунктов. Работы ведутся автономно: каждый логический этап проходит тесты, commit, push и соответствующий production release. Если конкретный пункт временно блокируется внешним ограничением, он фиксируется как блокер с причиной и безопасным обходом, после чего выполняются следующие независимые пункты. Изменения, которые улучшают архитектуру, безопасность, стоимость или качество результата, допускаются без ожидания пользователя, но фиксируются в ADR, changelog или итоговом отчёте.


## 12. Local-first вложения в Chat

Chat принимает до четырёх вложений за одно сообщение. Для текстовых и исходных файлов Agent Room извлекает ограниченный локальный excerpt в браузере и добавляет его в контекст **только после явного нажатия Send**. Перед отправкой в интерфейсе видно `Shared on send`. Бинарные, PDF, архивные и другие неподдерживаемые типы остаются на устройстве и помечаются `Local only`; они не загружаются автоматически и могут быть исследованы только через явную локальную задачу или текстовый экспорт. Общий payload остаётся ниже API-границы сообщения, приоритет всегда у собственного текста пользователя.
